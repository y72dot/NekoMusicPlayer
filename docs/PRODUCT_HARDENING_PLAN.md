## 1. 目标与边界

本方案将项目从“已有较完整功能和自动化测试的前端原型”推进到“生产链路明确、播放行为可靠、界面可用、数据可治理、外部适配器可维护、问题可诊断”的产品状态。

本轮按以下固定顺序推进：

1. 生产链路与线上可用性。
2. 核心播放可靠性。
3. UI/UX 基础重做。
4. 数据安全与存储治理。
5. 数据源适配器平台化。
6. 可观测性与问题诊断。

本轮不实施歌词、跨设备同步、新数据源、账号系统或未经评审的产品功能。外部平台能力不得以绕过 DRM、访问控制或服务条款为目标。

## 3. 当前问题判断

### 3.1 生产链路

- 网易云和 Bilibili 客户端请求相对路径 `/api/*`。
- Vite 开发服务器提供这些代理，但 `dist` 是纯静态产物，不包含代理服务。
- 当前仓库没有可审计的生产 Nginx 配置，无法证明线上数据源与本地行为一致。
- 部署工作流会切换版本目录，但缺少部署后 HTTP 烟雾检查和自动回滚。

### 3.2 播放核心

- 播放引擎以 `console.warn/error` 和零散 Toast 表达失败，没有稳定错误代码。
- `load()` 失败不向调用方返回明确结果，Store 难以决定重试、跳过或保持当前曲目。
- 原生媒体错误、自动播放限制、资源过期和适配器异常没有统一分类。
- 缺少显式 `idle/loading/ready/playing/paused/error` 状态，界面无法正确反馈加载过程。

### 3.3 UI/UX

- 缺少统一颜色、字号、间距、控件和焦点规范。
- 主框架固定 220px 侧栏，几乎没有小屏布局。
- 控制栏使用未标注的 Emoji，缺少当前曲目信息、按钮名称和禁用状态。
- 多处仍使用浏览器 `prompt/confirm`，状态反馈和国际化不一致。
- 键盘焦点、ARIA、Toast live region 和对比度尚未系统治理。

### 3.4 数据与凭据

- `db.ts` 和 `audioCache.ts` 分别打开同一个 IndexedDB，版本与 Store 名称重复。
- 缓存有固定上限，但用户无法配置、按来源清理或获知配额压力。
- 导入数据缺少明确 Schema 版本和系统化校验。
- 流媒体 Cookie 以普通文本输入并持久化到 LocalStorage，需要更清晰的风险控制。

### 3.5 适配器

- `SourceAdapter` 只定义解析和加载，没有能力声明、健康状态和统一错误契约。
- 外部服务错误主要以英文字符串传递，上层依赖字符串判断或通用失败提示。
- 开发代理允许从请求路径提取 Bilibili CDN 主机名，需要生产级白名单约束。

### 3.6 可观测性

- 日志只输出到控制台，没有有界内存记录、脱敏或用户可导出的诊断报告。
- 缺少全局 `error`、`unhandledrejection` 捕获。
- 用户无法一键提供应用版本、浏览器、存储占用、适配器状态和最近错误。

## 4. 实施原则

1. **播放不中断优先**：辅助功能失败不得破坏本地文件播放和现有队列。
2. **错误可行动**：用户看到的错误必须说明发生了什么以及下一步怎么办。
3. **不泄露凭据**：Cookie、Token、签名参数、完整媒体 URL 不进入日志、诊断和测试附件。
4. **生产开发一致**：开发代理与生产代理共享路径、白名单、超时和响应约定。
5. **数据可迁移**：所有持久化结构有版本、校验、升级和失败回退。
6. **渐进式体验升级**：保持现有路由和核心操作，避免 UI 重做与业务重写同时发生。
7. **测试分层**：纯逻辑使用单测，浏览器状态使用 E2E，真实外部服务烟雾测试不作为每次提交的确定性门禁。

5. 部署后检查首页、静态资源和 API 代理；失败时恢复上一个 `current` 软链接。

- 将 Nginx 配置安装到生产服务器并执行 `nginx -t`。
- 推送后观察 Actions，并执行真实线上烟雾检查。

- 部署脚本在健康检查失败时不会保留失败版本为 `current`。
- 文档能够由未参与开发的维护者复现部署与回滚。

## 6. 阶段 2：核心播放可靠性

### 目标

让加载、播放、失败、重试和跳过形成确定的状态机。

### 实施

1. 定义 `PlaybackError`：错误代码、阶段、是否可重试、用户建议和安全上下文。
2. 定义播放状态：`idle/loading/ready/playing/paused/error`。
3. `load()` 返回明确成功或抛出类型化错误；失败时不留下半初始化音频状态。
4. 分类处理：资源不存在、认证过期、限流、超时、浏览器格式不支持、自动播放受限、网络异常和未知错误。
5. 对短暂网络/远程 URL 失败提供一次受控重载；不对认证和版权错误盲目重试。
6. 队列自然播放遇到不可用曲目时，在有下一首的情况下提示并跳过；限制一次跳过链，防止死循环。
7. 将播放核心日志接入统一 Logger，禁止直接打印完整 Track/URL。
8. 为快速切歌、加载竞态、错误恢复、队列边界和刷新恢复补测试。

### 验收

- Store 始终能读取确定的播放状态和最后错误。
- 失败曲目不会让界面永久显示“正在播放”。
- 快速切歌时旧请求不能覆盖新曲目。
- 本地文件播放不依赖远程适配器健康状态。

## 7. 阶段 3：UI/UX 基础重做

### 目标

建立一致、响应式、可键盘操作的产品界面骨架。

### 实施

1. 增加全局 Design Tokens：颜色、排版、间距、圆角、阴影、层级、动画和焦点环。
2. 重构应用框架：桌面侧栏、小屏顶部/底部导航和安全区适配。
3. 重做控制栏：封面、曲目信息、上一首/播放/下一首、进度、时间、音量、模式及加载/错误状态。
4. 统一按钮、输入、卡片、列表、空状态、错误状态和 Loading 视觉。
5. 为交互控件补可访问名称、`aria-current`、焦点顺序、键盘行为和最小触摸面积。
6. Toast 使用 live region；减少纯颜色或 Emoji 表达。
7. 把高风险 `prompt/confirm` 逐步替换为应用内对话框；本阶段优先处理清缓存和新建歌单。
8. 增加桌面与移动视口 E2E，避免仅凭截图验收。

### 验收

- 360px 宽度无横向溢出，导航和播放控制可用。
- 所有核心按钮拥有稳定可访问名称和焦点样式。
- 加载、空、禁用和错误状态清晰且中英文可用。
- 原有关键流程 E2E 保持通过。

## 8. 阶段 4：数据安全与存储治理

### 目标

让用户数据可升级、可备份、可清理，并降低凭据泄露风险。

### 实施

1. 建立唯一数据库模块，集中 DB 名称、版本、Store、事务和升级逻辑。
2. 为设置、歌单导出和缓存元数据定义 Schema 版本及运行时校验。
3. 数据升级失败时保留旧数据并提供可行动错误，不静默覆盖。
4. 读取 `navigator.storage.estimate()`，展示使用量和配额；空间不足时停止缓存而不是影响播放。
5. 缓存支持用户配置上限、按来源统计/清理和 LRU/TTL 说明。
6. Cookie 字段改为密码输入，支持显隐和独立清除；禁止诊断导出具体值。
7. 增加“导出备份”“导入校验”“清除所有本地数据”的明确入口和二次确认。
8. 覆盖版本迁移、配额不足、损坏备份和清理失败测试。

### 验收

- 同一数据库只存在一个打开与升级实现。
- 无效备份不能部分污染现有数据。
- 清缓存、清凭据和清全部数据的边界明确。
- Cookie 不以明文展示，也不进入日志或诊断包。

## 9. 阶段 5：数据源适配器平台化

### 目标

使外部数据源具备统一能力描述、健康状态和错误语义。

### 实施

1. 扩展适配器契约：能力、认证要求、健康检查和显示状态。
2. 定义 `AdapterErrorCode`：认证、限流、超时、未找到、版权/访问限制、代理不可用、解析失败和未知错误。
3. NetEase、Bilibili、文件和外链适配器统一抛出结构化错误。
4. UI 使用错误代码映射本地化文案，不解析英文错误字符串。
5. 设置页展示适配器状态、认证状态和最近检查时间；真实检查由用户触发。
6. 固定契约 Fixture 和 Mock，真实烟雾任务独立且不记录凭据。
7. API/代理白名单作为共享配置或生成来源，减少开发/生产漂移。

### 验收

- 上层不依赖第三方原始错误字符串做业务判断。
- 任一适配器不可用不会阻塞应用启动及其他来源。
- 健康检查有超时、可取消且不自动泄露认证信息。

## 10. 阶段 6：可观测性与问题诊断

### 目标

让用户能安全地描述问题，让维护者获得足够但不敏感的证据。

### 实施

1. Logger 增加有界环形缓冲、结构化级别、时间、命名空间和错误代码。
2. 中央脱敏器移除 Cookie、Token、Authorization、签名参数、查询串和 Blob URL。
3. 捕获全局脚本错误和未处理 Promise，记录为脱敏诊断事件。
4. 生成 JSON 诊断报告：版本、构建信息、浏览器、PWA、存储估算、缓存统计、适配器状态、播放状态和最近日志。
5. 设置页提供预览、复制/下载和“诊断不含凭据”的说明。
6. 默认不上传任何遥测；未来若增加匿名统计，必须单独评审并显式选择加入。
7. 为脱敏器、缓冲上限、全局捕获和报告 Schema 补测试。

### 验收

- 自动测试证明常见 Cookie、Token、URL 查询参数不会出现在报告中。
- 日志有固定上限，不造成无限内存增长。
- 断网时也能生成诊断报告。
- 用户无需打开开发者工具即可导出问题证据。

## 12. 风险与回滚

| 风险 | 控制 | 回滚 |
| --- | --- | --- |
| 生产代理配置错误 | `nginx -t`、白名单、部署后健康检查 | 恢复上一 `current` 版本和上一 Nginx 配置 |

## 15. 2026-08-15 播放回归处置

线上浏览器日志确认了两条相互放大的故障链：网易播放地址接口发生瞬时超时时，阶段 2 引入的自动恢复会对队列中的后续曲目递归执行相同请求；网易接口偶尔返回 `http://*.music.126.net` 音频地址时，HTTPS 页面又会因混合内容策略拒绝加载。

处置范围：

1. 仅对网易自有 `music.126.net` 音频域名把 HTTP 地址升级为 HTTPS，保留签名查询参数，不放宽到任意主机。
2. 加载状态下禁用播放按钮，并忽略同一曲目的重复播放请求，避免用户等待时产生并发请求。
3. 网络、超时和限流等来源级可重试错误不再自动遍历队列；版权、格式或单曲资源不可用仍可跳过。
4. 增加协议升级、超时不级联和加载中防重复操作的单元回归测试。

验证要求：类型检查、全部单元测试、生产构建和 E2E 均通过后再部署；部署后重点观察网易播放地址 POST 数量、混合内容告警和连续切歌行为。

## 16. 2026-08-15 部署方式调整

生产部署从 GitHub Actions 自动 SSH 发布改为服务器端人工触发：删除生产部署 workflow，GitHub Actions 仅保留 `main`/Pull Request 质量检查；服务器通过 `ops/deploy/deploy-from-server.sh` 获取远端提交、隔离构建、执行质量门禁、创建版本目录、原子切换、健康检查和失败回滚。原有 `manage-release.sh` 继续负责版本状态与最近五版清理。

此决策取代本文之前关于 GitHub `production` Environment、SSH Secrets、Actions Artifact 和自动部署的待办要求；这些段落仅保留为历史执行记录，不再是当前生产操作规范。当前规范以 `docs/PRODUCTION_DEPLOYMENT.md` 为准。

## 17. 2026-08-15 网易 CDN 二次回归处置

第二份线上日志确认：直接把网易返回的 HTTP 签名音频 URL 升级为 HTTPS 会导致 CDN 返回 403，浏览器直连 CDN 的元数据 `fetch` 同时受 CORS 限制。协议升级方案因此撤回，改为严格白名单的同源 `/api/netease-media/<http|https>/<host>/...` 代理；代理保留原始协议、主机、路径和签名查询参数，只允许 `*.music.126.net`，并向上游设置网易 Referer。开发服务器与生产 Nginx 使用相同的目标校验规则。
