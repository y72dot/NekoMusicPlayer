## 1. 方案目的

本方案用于将 NekoMusicPlayer 从“核心功能已具备、工程质量尚未闭环”的状态，推进到“可重复验证、可稳定发布、可持续迭代”的状态。

方案重点解决以下问题：

1. 恢复 TypeScript 类型检查，使代码、依赖和构建工具形成一致的类型基线。
2. 分离单元测试与端到端测试，修复当前测试命令边界不清的问题。
3. 收敛端到端测试失败和超时，形成稳定、可复现的回归测试集。
4. 将类型检查、单元测试、构建和必要的端到端测试接入持续集成。
5. 对齐版本号、更新日志、README、发布标签与实际功能状态。
6. 建立正式的需求、路线图和版本治理方式，为后续功能开发提供依据。

本方案不直接承诺新的产品功能。当前仓库中没有开放的 Issue、PR、Milestone、Roadmap 或明确 TODO，因此任何新增功能都必须在需求评审后进入实施计划。

### 2.7 阶段 3 执行记录

阶段 3 于 2026-08-13 完成。单 worker 基线将原先失败稳定收敛为 8 项，确认均为测试定位和运行器生命周期问题，而不是产品主流程回归：

- Bilibili 区域复用了 `.netease-row` 和 `.cookie-warning`，导致网易云用例的旧选择器同时命中多个元素。
- 中文批量操作用例直接选择面板中的全部 `textarea`，新增数据源后产生严格模式冲突。
- URL 导入 Toast 用例错误假设默认浏览器语言一定为中文。
- Playwright 内置 `webServer` 在当前 Windows 环境中无法可靠清理 Vite 子进程，造成测试全部执行完后命令仍不退出。

实施修复如下：

- 为外部链接和网易云导入控件增加稳定的 `data-testid`，并让 Page Object 只定位对应区域。
- 国际化用例复用 `ImportPage`，非国际化 Toast 用例同时接受中英文消息。
- 网易云类型选项测试验证稳定的 option value，而不是依赖浏览器默认语言。
- 增加 `scripts/run-playwright.mjs`，显式启动、健康检查和清理 Vite，在 Windows 与类 Unix 环境管理服务器生命周期。
- Playwright HTML 报告设置为不自动打开，配置允许外部启动器禁用内置 webServer。

## 3. 总体实施原则

1. **先基线、后扩展**：P0 工程问题未关闭前，不安排大规模新功能开发。
2. **每阶段可独立验收**：每个阶段必须产生明确交付物，并通过可执行命令验证。
3. **测试分层**：单元测试关注业务逻辑，端到端测试关注关键用户路径，避免职责混用。
4. **禁止掩盖问题**：不得仅通过关闭类型检查、批量跳过测试或无条件提高超时来制造“通过”。
5. **小批量合并**：每个阶段拆为可审查的短分支或 PR，减少交叉影响。
6. **发布可追溯**：版本、提交、构建、变更日志和发布标签必须形成一一对应关系。
7. **外部服务可隔离**：网易云和 Bilibili 的自动化测试应尽量使用稳定 Mock；少量真实接口检查独立运行。

2. 执行并保存以下基线结果：

   - `npm run test:e2e`

4. 冻结本轮范围：只处理工程质量、发布和文档，不同时重构播放器核心逻辑。
5. 明确本轮目标版本号。建议将当前大量新增能力归入 `0.3.0`；若项目坚持现有语义，也可先发布 `0.2.1`，但必须统一所有版本信息。

- 本轮不包含未经评审的新产品功能。

#### 风险与控制

- **风险**：本地 `node_modules` 与锁文件不一致。  
  **控制**：在干净环境执行 `npm ci` 或明确记录使用 `npm install --legacy-peer-deps` 的原因。
- **风险**：外部 API 或网络限制导致基线波动。  
  **控制**：将真实网络检查与确定性测试分开记录。

### 阶段 1：恢复类型安全与依赖一致性

**目标**：使 `npm run typecheck` 稳定通过，并消除工具链明显的类型版本冲突。

**建议工期**：1～2 人日。

**依赖**：阶段 0 完成。

#### 工作内容

1. 检查并补齐直接使用的类型依赖：
   - `@types/node`
   - 与 Vue I18n 当前版本匹配的 `@intlify/devtools-types` 或正确的 Vue I18n 依赖组合。
2. 对齐 TypeScript、Vite、Vitest、Vue Test Utils 和相关传递依赖版本，消除两套不兼容 Vite 类型并存造成的 `ImportMeta.hot` 冲突。
3. 修复 `src/adapters/fileSystemAdapter.ts` 中封面数据传给 `Blob` 的类型问题：
   - 明确复制为由 `ArrayBuffer` 支持的字节数组；或
   - 使用安全的 `ArrayBuffer` 切片。
4. 检查 `tsconfig.json` 的 `lib`、`types`、`moduleResolution` 和测试类型配置。
5. 评估是否需要 `skipLibCheck`：
   - 优先修复依赖版本和缺失类型；
   - 只有确认剩余问题完全来自第三方声明且风险可接受时才启用；
   - 若启用，必须在 Issue 中记录原因和移除条件。
6. 用干净安装环境重复验证，避免只对当前 `node_modules` 生效。

#### 交付物

- 更新后的依赖清单与锁文件。
- 修复后的 TypeScript 源码和配置。
- 依赖选择及兼容性说明。

#### 验收标准

- `npm run typecheck` 退出码为 0。
- `npm run build` 仍然通过。
- 源码单元测试仍为 175 项或更多且全部通过。
- 不存在通过 `any`、`@ts-ignore` 或不受控类型断言绕过核心问题的修改。
- 在一次干净依赖安装后可以重复通过。

#### 回滚条件

如果依赖升级造成大面积运行时回归，优先回滚到阶段 0 的锁文件，改用最小依赖补丁方案，不在同一变更中进行跨主版本升级。

### 阶段 2：重构测试命令和测试边界

**目标**：让每个测试命令只运行其负责的测试层，并提供统一的本地验证入口。

**建议工期**：0.5～1 人日。

**依赖**：可与阶段 1 部分并行，最终需在阶段 1 后复验。

#### 工作内容

1. 在 Vitest 配置中设置明确的 `include` 和 `exclude`：
   - 包含 `src/**/*.spec.ts`；
   - 排除 `e2e/**`、`dist/**`、`playwright-report/**` 和 `test-results/**`。
2. 保留 Playwright 的 `testDir: './e2e/specs'`，确保端到端测试只由 Playwright 执行。
3. 调整 `package.json` 脚本，建议形成以下语义：
   - `test`：运行单元测试一次，适合 CI；
   - `test:watch`：Vitest 监听模式；
   - `test:unit`：显式运行单元测试；
   - `test:e2e`：运行 Playwright；
   - `test:all`：依次运行类型检查、单元测试和端到端测试；
   - `check`：运行类型检查、单元测试和构建。
4. 更新 README 中的测试命令说明，区分日常开发、提交前检查和完整回归。
5. 确认测试过程中不会意外请求真实 Bilibili/网易云 CDN；若存在，补 Mock 或拆分为独立集成测试。

#### 交付物

- 更新后的 Vite/Vitest 配置。
- 清晰的 npm 测试脚本。
- 更新后的测试说明。

#### 验收标准

- `npm test` 只收集 23 个源码测试文件或后续新增的源码测试文件。
- `npm test` 不加载任何 `e2e/specs` 文件。
- `npm run test:e2e -- --list` 只列出 Playwright 测试。
- 单元测试不依赖外部网络即可完成。
- 失败命令的退出码能被 CI 正确识别。

### 阶段 3：收敛端到端测试与关键用户路径

**目标**：修复现有失败，降低执行波动，使关键路径端到端测试可在合理时间内稳定完成。

**建议工期**：2～4 人日。

**依赖**：阶段 2 完成。

#### 已观察失败范围

第一轮验证中至少观察到以下失败类别：

1. 中文环境下批量操作栏的断言失败。
2. URL 导入后的 Toast 断言失败。
3. 网易云导入区域可见性失败。
4. 网易云 Cookie 警告和设置页跳转失败。
5. 网易云 Cookie 保存后状态更新失败。
6. 网易云类型选择器选项断言失败。
7. 未配置 Cookie 时错误 Toast 断言失败。
8. 全量测试在 180 秒内未完成。

以上失败必须逐项判断为：真实功能缺陷、国际化文案变化、测试选择器过期、共享状态污染、并发问题或外部网络依赖。

#### 工作内容

1. 先使用单 worker 和失败重跑定位：
   - 将失败用例逐文件运行；
   - 记录截图、Trace、控制台错误和网络请求；
   - 区分确定性失败与并发波动。
2. 修复选择器策略：
   - 优先使用角色、可访问名称和稳定 `data-testid`；
   - 避免依赖易变化的 DOM 层级和完整文案；
   - 国际化测试只在验证翻译时断言精确文案。
3. 修复测试隔离：
   - 每个测试清理 LocalStorage、IndexedDB、Cache Storage 和 Service Worker 状态；
   - 避免跨 worker 共享固定账号或可变远端数据；
   - 使用独立的测试数据 ID。
4. 修复外部服务测试：
   - 网易云、Bilibili API 使用请求拦截和固定响应；
   - 真实服务烟雾测试单独标记，不纳入每次提交的必过门禁；
   - Cookie 不写入日志、Trace 或测试报告。
5. 评估全量并发：
   - 在本地和 CI 分别测量 1、2、4 worker；
   - 不盲目使用 10 worker；
   - 根据资源限制确定 CI 的稳定并发数。
6. 建立关键路径烟雾测试集：
   - 应用启动及导航；
   - 本地文件导入；
   - 音乐库播放；
   - 刷新后队列和 Blob 恢复；
   - 歌单创建、添加、播放；
   - 设置保存；
   - 网易云/Bilibili Mock 导入。
7. 清理仅用于诊断的控制台输出，保留失败时有价值的附件。

#### 交付物

- 修复后的端到端用例和必要的产品代码。
- 稳定的 Mock/Fixture。
- `smoke` 与 `full` 两个测试集合。
- 一份失败分类与修复记录。

#### 验收标准

- 连续运行完整 E2E 测试至少 3 次全部通过。
- CI 推荐环境中的单次完整执行时间目标不超过 10 分钟。
- 烟雾测试目标不超过 3 分钟。
- 不允许存在未说明的 `skip`、`fixme` 或仅靠增加超时解决的用例。
- 测试日志和附件不包含 Cookie、Token 等敏感信息。

#### 风险与控制

- **风险**：Service Worker 和缓存造成用例串扰。  
  **控制**：测试环境关闭非必要 PWA 注册，或在每个上下文显式注销并清理缓存。
- **风险**：真实音频播放受浏览器策略影响。  
  **控制**：保留确定性的音频 Mock，同时设置少量独立真实媒体回归。
- **风险**：外部站点接口变化。  
  **控制**：契约测试与真实烟雾测试分离，适配器解析使用固定 Fixture。

### 阶段 4：建立 CI 质量门禁和安全部署链路

**目标**：确保未通过质量检查的提交不能自动部署。

**建议工期**：1～2 人日。

**依赖**：阶段 1～3 完成。

#### 工作内容

1. 新增独立 CI 工作流，触发范围至少包括：
   - 对 `main` 的 Pull Request；
   - 推送到 `main`；
   - 手工触发。
2. CI Job 建议拆分为：
   - `typecheck`；
   - `unit-test`；
   - `build`；
   - `e2e-smoke`；
   - 可按条件运行的 `e2e-full`。
3. 使用锁文件进行确定性安装，解决当前部署工作流使用 `npm install --legacy-peer-deps` 的长期风险。
4. 缓存 npm 下载内容，但不缓存不可控的完整 `node_modules`。
5. 上传失败时的 Playwright Trace、截图和报告，并设置合理保留期。
6. 调整部署工作流：
   - 部署必须依赖质量 Job 成功；
   - 构建产物由同一提交生成；
   - 避免质量检查与部署使用不同依赖结果。
7. 检查部署凭据：
   - 只使用 GitHub Secrets；
   - 日志不得回显密码、Cookie 或 Token；
   - 对 `sshpass` 方案进行风险评估，并制定迁移回受限 SSH Key 或部署令牌的计划。
8. 为 `main` 配置分支保护，要求核心检查通过后才能合并。

#### 交付物

- CI 工作流文件。
- 更新后的部署工作流。
- 分支保护和必需检查清单。
- CI 使用说明及失败排查入口。

#### 验收标准

- 故意制造类型错误时 CI 必须失败且不能部署。
- 故意制造单元测试失败时 CI 必须失败且不能部署。
- 烟雾测试失败时可下载 Trace/截图。
- 全部检查通过时，构建和部署使用同一提交。
- 主分支不能绕过规定的必需检查，管理员应只在事故处置时例外操作。

### 阶段 6：建立下一周期产品路线图

**目标**：将后续开发从临时想法转变为有依据、有优先级、有验收标准的路线图。

**建议工期**：1 人日完成首次规划，之后持续维护。

**依赖**：可以在阶段 4 后开始，但不阻塞阶段 5 发布。

#### 工作内容

1. 建立需求入口：GitHub Issue 模板至少包括 Bug、Feature、Adapter 和 Technical Debt。
2. 创建 Milestone，例如：
   - `0.3.x 稳定性维护`；
   - `0.4.0 下一功能版本`；
   - `Backlog`。
3. 每项需求必须包含：
   - 用户问题或使用场景；
   - 明确范围与非目标；
   - UI/交互说明；
   - 数据迁移与兼容性影响；
   - 安全、版权、隐私和外部 API 风险；
   - 验收标准；
   - 测试方案。
4. 使用简单评分进行排序：用户价值、覆盖人数、实现成本、维护风险和外部依赖风险。
5. 每个版本只选择容量可控的需求，并预留约 20% 容量处理缺陷和依赖升级。
6. 每月或每个发布周期复盘一次：删除失效需求，调整优先级，记录决策原因。

#### 候选需求池

以下仅是待评审候选项，不属于已经批准的实施计划：

- 移动端和小屏响应式体验专项优化。
- Media Session API、系统媒体键和锁屏控制。
- 歌词获取、解析、同步和离线缓存。
- 播放历史、收藏、最近播放和智能列表。
- 跨设备同步或可选云端备份。
- 更多来源适配器及统一的适配器健康状态页。
- 缓存上限、LRU 淘汰和按来源清理策略。
- 无障碍键盘导航、屏幕阅读器和对比度专项。
- 错误监控、匿名性能指标和用户可控诊断导出。
- 更严格的 Content Security Policy 和代理目标白名单。

候选项进入开发前，必须经过需求确认和风险评估，尤其要考虑流媒体平台条款、版权、Cookie 安全以及接口稳定性。

#### 交付物

- `ROADMAP.md` 或 GitHub Project。
- Issue 模板、标签和 Milestone。
- 已排序的需求池。
- 下一版本范围说明。

#### 验收标准

- 每个“计划中”事项都有 Issue、负责人、版本归属和验收标准。
- Roadmap 明确区分 `Now`、`Next`、`Later` 和“不做”。
- 未评审候选不会被写成已经承诺的版本功能。

## 7. 质量门禁定义

| Cookie 泄露 | 中 | 高 | Secret 管理、禁止日志输出、报告脱敏、最小化存储 |
| 浏览器跨域或媒体策略变化 | 中 | 高 | 代理边界测试、用户手势播放、兼容性矩阵 |
| IndexedDB 数据升级破坏用户数据 | 中 | 高 | 版本化迁移、备份/导出、升级测试 |
| PWA 缓存旧资源 | 中 | 中 | 缓存版本策略、更新提示、E2E 覆盖升级场景 |
| E2E 并发导致不稳定 | 高 | 中 | 状态隔离、合理 worker 数、Trace 和失败重试分析 |
| 依赖升级引入破坏性变化 | 中 | 中 | 小版本升级、锁文件、自动化回归、分批合并 |
| 部署凭据或服务器不可用 | 中 | 高 | 最小权限、凭据轮换、回滚产物、部署前检查 |
| README 与代码再次漂移 | 中 | 中 | PR 模板要求文档影响检查，发布门禁核对 |

## 10. 责任分工建议

若由一人实施，可按阶段顺序执行；若由多人协作，建议角色如下：

| 角色 | 主要职责 |
| --- | --- |
| 技术负责人 | 范围、依赖决策、质量门禁、发布批准 |
| 前端开发 | 类型修复、产品缺陷、适配器和 UI 修改 |
| 测试负责人 | 测试边界、E2E 稳定性、回归报告 |
| DevOps/维护者 | CI、部署、凭据、回滚与线上验证 |
| 文档/发布负责人 | README、CHANGELOG、版本、Release |

每个 Issue 只能有一个直接负责人，但可设置评审人。P0 项必须明确完成日期和阻塞说明。

## 11. 完成定义（Definition of Done）

本轮计划只有在同时满足以下条件后才能整体标记为完成：

1. 类型检查、单元测试、构建和完整端到端测试全部稳定通过。
2. CI 对 Pull Request 和主分支执行质量门禁，失败时不会部署。
3. 已发布版本的源码、文档、tag、构建产物和 Release 完全对应。
4. README 覆盖当前实际功能、配置、测试和故障排查。
5. 没有未说明的 P0/P1 问题。
6. 后续需求通过 Issue/Milestone/Roadmap 管理，不再依赖散落注释或口头计划。
7. 生产环境完成部署后烟雾测试，并确认可执行回滚。

## 12. 建议的下一步行动

1. 推送阶段提交并观察 Pull Request 与 `main` 的首次 GitHub Actions。
2. 按发布检查记录配置 `production` Environment 和分支保护；主机公钥固定在工作流中，不要求额外 Secret。
3. CI 通过后执行生产部署、烟雾测试和回滚确认。
4. 在已验证提交上创建 `v0.3.0` 标签与 GitHub Release。
5. 建立 Roadmap 建议的远端标签和 Milestone，并为进入 `Now` 的事项关联 Issue、负责人和验收标准。
